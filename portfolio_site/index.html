Problem

LLM 추천에는 정답이 없다.
그래서 기준을 만들었다.

기존 음악 스트리밍 서비스는 사용자가 직접 기분·장르를 선택합니다. DIP는 위치·활동 목표·주변 소음(dB)을 LLM이 해석해 그 순간에 맞는 플레이리스트를 자동으로 구성합니다. 그런데 "잘 됐다"는 기준을 어떻게 정의할 것인가, 라는 근본적인 문제가 남았습니다.

⚠️
정답 레이블이 없다
Precision, Recall, NDCG 같은 추천 시스템 표준 지표는 모두 "정답"을 전제합니다. 하지만 "이 상황에서 실제로 들을 법한 음악"이라는 정답 데이터가 존재하지 않습니다.
🎯
측정하지 않으면 개선할 수 없다
서비스의 개선 방향을 "느낌"이 아닌 데이터로 결정하려면, 먼저 무엇을 어떻게 측정할지를 정의해야 합니다. 평가 체계 설계 자체가 첫 번째 과제였습니다.
📊
추천 로직의 근거가 "감"이었다
"집중할 땐 lofi가 좋다"는 직관은 있지만, 수치 근거는 없었습니다. 어떤 소음 수준, 어떤 목표 조합에 어떤 음악이 맞는지를 데이터로 정의해야 했습니다.
🔗
범용적인 문제다
LLM 출력물의 품질 평가는 뉴스 요약, AI 글쓰기 보조, 챗봇 등 모든 LLM 서비스가 공통으로 직면하는 미해결 문제입니다.
핵심 과제 정의
"LLM 음악 추천 서비스에서 추천이 상황에 적합한지를 측정하고, 그 결과를 바탕으로 시스템을 개선하는 피드백 루프를 만들어라."

Analysis Process

어떻게 분석했는가

단순 나열이 아닌, 각 단계가 왜 필요했는지와 어떤 의사결정을 했는지 중심으로 설명합니다.

1
문제 재정의 — "정확함"이란 무엇인가
추천 시스템 표준 평가 지표(Precision, Recall, NDCG)는 모두 정답 레이블을 전제합니다. LLM 추천에서는 "사용자가 이 상황에서 실제로 들을 법한 음악"이라는 정답 데이터가 없습니다. 평가 자체가 문제였습니다.
표준 지표를 포기하고, 서비스 맥락에서 "잘 됐다"는 행동 신호를 찾는 방향으로 전환
2
외부 데이터 3종 분석 — 추천 로직 근거 수치화
환경공단 · RAED · Spotify 데이터를 각각 분석한 후 연결해 소음×목표×위치 조합에 수치 기준을 부여했습니다. 핵심 발견은 "장소보다 행동이 소음을 더 강하게 결정한다"는 점이었고, 이것이 실시간 소음 측정이 필수라는 설계 근거가 됐습니다.

Key Findings

데이터가 말한 것

6가지 분석 결과, 수치보다 중요한 것은 수치가 의미하는 맥락입니다.

01
85%가 실제로 들으러 갔다 — 하지만 전부가 아니다
전체 DLC 85.15%는 강점입니다. 그러나 상황별로 보면 뚜렷한 약점이 드러납니다. 공공 공간(카페, 도서관)에서 개인적인 감정 케어(분노, 위로)를 요청하는 조합에서 전환율이 급락합니다. 어디가 문제인지 특정했다는 것 자체가 성과입니다.

02
응답 시간은 단순히 줄어들지 않았다 — 급등, 그리고 급락
상관계수(-0.2231)만 보면 "시간이 지날수록 빨라졌다"로 읽힙니다. 그러나 실제 시계열은 안정(7초대) → 개인화 도입 후 급등(14초대) → 최적화 후 급락(3초대)입니다. 수치 하나보다 패턴이 더 많은 것을 말해줍니다.
응답 시간 (초)
개인화 기능 도입 (Jan 6)
성능 최적화 시작 (Jan 12)
인사이트: 신기능 도입 직후 성능 저하는 예측 가능한 패턴입니다. 변경 직후 일주일간 집중 모니터링 체계가 필요하다는 구체적 근거입니다.

04

05
RMSE 1.14 — "틀린 모델"의 가치
지연 시간만으로 만족도를 예측하는 모델의 오차가 평균 1점 이상입니다. 이 결과의 진짜 가치는 틀렸다는 사실 자체에 있습니다.

단순 모델 (가설):

Predicted = 4.0 − 0.15 × latency_sec

→ RMSE = 1.1353 (4점 만점 척도에서 1점 이상 틀림)

인사이트: "빠르면 만족한다"는 직관을 수치로 반박했습니다. 만족도를 설명하는 더 중요한 변수는 콘텐츠 품질(Context Accuracy, 장르 일치도)입니다. 성능 최적화보다 맥락 정확도 개선에 개발 리소스를 우선 배분해야 한다는 데이터 기반 근거입니다.
06
일관된 맥락 사용 패턴 — 설계 검증
사용자들은 무작위로 서비스를 사용하지 않았습니다. 카페×집중·활력, 집/실내×휴식·수면, 코워킹×집중·활력, 헬스장×활력 조합이 일관되게 나타났습니다. 이것은 단순한 사용 현황 이상의 의미를 가집니다.
인사이트: RAED 데이터를 바탕으로 설계한 추천 로직이 실제 사용 맥락과 정합한다는 간접 검증입니다. 외부 데이터 기반 설계 근거가 실제로 작동했습니다.

Differentiation

이 프로젝트를 다르게 만드는 것

대부분의 포트폴리오 프로젝트는 있는 데이터를 분석합니다. 이 프로젝트는 그것과 다른 네 가지를 담고 있습니다.

1
분석 환경 설계
"분석할 환경"을 직접 만들었다
필요한 데이터가 존재하지 않는 상황에서, 사전배포를 제안하고 로그 스키마를 직접 설계해 데이터를 만들었습니다. "측정할 수 없으면 개선할 수 없다. 그렇다면 측정 가능한 상태부터 만들어야 한다."
실무에서 분석에 필요한 로그가 항상 존재하지 않습니다. 무엇을 어떻게 수집할지를 설계할 수 있는 분석가는 수동적 수용자가 아닌 시스템의 공동 설계자입니다.
2
KPI Zero-Design
없던 기준을 직접 만들었다
Precision, Recall처럼 계산만 하면 되는 지표가 아니라, "이 서비스에서 좋은 추천이란 무엇인가"라는 질문 자체를 정의했습니다. 8개 후보 중 3개가 탈락한 사유를 기록하고, 각 지표의 한계를 함께 명시했습니다.
수치를 만드는 것보다 그 수치를 얼마나 신뢰할 수 있는지를 아는 것이 더 어렵습니다. 지표의 한계를 함께 제시하는 태도는 잘못된 결정을 막는 핵심 역량입니다.
3
분석 → 결정
분석이 실제 결정으로 이어졌다
이탈 원인 분석 → 팀 공유 → 개발 우선순위 변경. 보고서가 서랍 속에 들어가지 않고 팀의 행동을 실제로 바꿨습니다. 분석가의 가장 중요한 역할인 "분석 결과를 조직 결정으로 연결"을 직접 경험했습니다.
분석가의 가치는 수치를 계산하는 것이 아니라 그 수치가 조직 결정에 영향을 미칠 때 실현됩니다.
4
이종 데이터 연결
연결이 새로운 임계값을 만들었다
환경공단(장소별 소음) + RAED(행동별 실제 소음) + Spotify(음악 특성)를 연결해 "카페+40dB = lofi, 카페+60dB = 팝"이라는 수치 기반 추천 기준을 만들었습니다. 단일 데이터셋 분석으로는 나올 수 없는 결론입니다.
데이터 결합 설계 자체가 분석 역량의 증거입니다. 연결이 없으면 "집중할 땐 lofi가 좋다"는 감에 머뭅니다.
Lessons Learned

잘 됐던 것과 아쉬운 것

한계를 솔직히 서술하는 분석가가 수치를 맹신하지 않습니다.

✅
잘 됐던 것
로그 스키마를 직접 설계한 덕에 분석에 필요한 데이터가 정확히 수집됐습니다. "어떤 데이터가 필요한지"를 먼저 정의하고 구현을 요청한 것이 핵심이었습니다.
⚠️
한계 — 표본 크기
18명의 응답에서 1~2명의 이탈이 전체 수치에 크게 영향을 미칩니다. 절대 수치보다 방향성 지표로 해석해야 하며, 인과 관계 증명에는 한계가 있습니다.
⚠️
한계 — 측정 기준의 관대함
Persona-Genre Accuracy 100%는 "완벽한 반영"이 아닌 "키워드 포함 기준"의 결과입니다. 수치의 의미를 측정 기준과 함께 해석해야 합니다.
💡
배운 것 — DB 설계의 중요성
Re-roll Rate가 DB 설계 이슈로 측정 불가능했습니다. 분석 관점을 데이터 수집 단계에서 미리 반영해야 한다는 교훈. 분석가가 DB 설계 단계부터 개입해야 하는 이유입니다.
💡
배운 것 — EDA가 ground truth
Spotify Audio Features API 403 차단 이후, EDA 분석으로 장르 특성을 직접 도출했습니다. API 없이도 데이터 기반 로직을 구현할 수 있었다는 발견은 제약 상황에서의 대안적 사고를 보여줍니다.
🔮
