---

## 1. 프로젝트 한 줄 소개

"LLM이 음악을 추천하면, 그 추천이 정말 맞는지 어떻게 알 수 있을까?" — DIP는 LLM 기반 상황 인식 음악 추천 서비스로, 정답 레이블도 표준 지표도 없는 환경에서 평가 기준 자체를 처음부터 설계한 프로젝트입니다. 팀 내 유일한 데이터 분석가로서 분석 방향·KPI·로그 스키마까지 전부 정의했으며, 팀 원안에 없던 사전배포를 직접 제안해 실사용자 데이터를 확보하고, 그 분석 결과가 실제 개발 우선순위를 바꾼 경험을 담고 있습니다.

---

## 2. 프로젝트 목적

### 왜 시작했는가

기존 음악 스트리밍 서비스는 사용자가 직접 기분이나 장르를 선택하는 방식에 의존합니다. 하지만 실제 음악이 필요한 순간은 훨씬 복합적입니다. "지금 카페에서 공부 중인데 옆 테이블 대화 소리가 꽤 크고, 발표 준비 때문에 집중이 필요하다"는 상황을 단순한 장르 선택으로는 담기 어렵습니다.

DIP는 사용자의 위치·활동 목표·주변 소음(dB)이라는 세 가지 맥락 정보를 LLM이 해석해 그 순간에 가장 맞는 플레이리스트를 자동으로 구성한다는 아이디어에서 출발했습니다.

### 어떤 문제의식이 있었는가

LLM에게 음악을 추천하게 하면 결과는 나옵니다. 하지만 세 가지 근본적인 질문이 남았습니다.

- 그 추천이 정말 이 상황에 맞는가?
- "잘 맞는다"는 기준을 어떻게 정의할 것인가?
- 시스템이 얼마나 잘 작동하고 있는지를 어떻게 측정할 것인가?

측정하지 않으면 개선할 수 없다는 판단에서, 데이터 분석가로서 이 세 질문에 답하는 것이 이 프로젝트의 핵심 과제가 됐습니다.

### 왜 중요한 문제인가

LLM 기반 서비스의 확산과 함께 "LLM 출력물의 품질을 어떻게 평가하는가"는 업계 전반에서 해결되지 않은 문제입니다. 정답 레이블이 없고, 개인마다 기준이 다른 콘텐츠 추천 영역에서 평가 체계를 설계하는 경험은, 어떤 LLM 서비스에도 적용 가능한 범용 역량입니다.

## 3. 비즈니스 문제

### 해결하려고 한 문제

LLM 음악 추천 서비스에서 "추천이 상황에 적합한지"를 측정하고, 그 측정 결과를 바탕으로 시스템을 개선하는 피드백 루프를 만드는 것입니다.

### 프로젝트 목표

| 목표 | 내용 |
|---|---|
| 추천 로직의 근거 수치화 | 외부 데이터로 "어떤 소음·목표엔 어떤 음악"을 감이 아닌 수치로 정의 |
| 평가 기준 설계 | 정답 레이블 없이 서비스 맥락에 맞는 자체 KPI 5개 도출 |
| 실사용자 검증 | 사전배포로 실제 로그를 수집하고, KPI를 실데이터로 측정 |
| 개선 방향 도출 | 분석 결과가 팀의 의사결정으로 연결되는 흐름 확보 |

### 핵심 KPI

| KPI | 측정 결과 | 의미 |
|---|---|---|
| Deep Link Conversion (DLC) | **85.15%** | 추천 결과를 실제로 들으러 간 비율 — 가장 행동 기반 지표 |
| Context-Sentiment Accuracy | **81.17%** | LLM이 사용자 상황을 추천 이유에 반영한 정확도 |
| Persona-Genre Accuracy | **100%** | 취향 정보 누락 없이 페르소나에 반영한 비율 |
| Agent Latency | **평균 7.62초** | 추천 생성 응답 시간 |
| Satisfaction RMSE | **1.1353** | 지연 시간만으로 만족도를 예측할 때의 오차 크기 |

### 성공 기준

- 사전배포로 실사용자 로그 확보 후 설계한 KPI를 전부 실측할 것
- 분석 결과가 팀 내 의사결정(기능 개발 우선순위 등)에 반영될 것

## 4. 사용 데이터

### 외부 데이터 3종 (추천 로직 근거 수립)

| 데이터셋 | 출처 | 규모 | 주요 변수 |
|---|---|---|---|
| 한국환경공단 환경소음 측정 데이터 | 공공데이터포털 (2024년) | `[확인 필요]` | 위치별 소음도(dBA), 측정지점, 용도 구분 |
| RAED (RealLife Activity & Environment Dataset) | Kaggle | 30,000행 | 행동, 위치(14종), 소음(dB), 활동량, 조도 |
| Spotify Music Dataset (High & Low Popularity) | Kaggle (Spotify API 수집) | `[확인 필요]` | energy, danceability, valence, tempo, loudness, instrumentalness, 장르 |

### 실사용자 로그 3종 (KPI 측정)

| 파일 | 내용 | 핵심 컬럼 |
|---|---|---|
| `playlists_final.xlsx` | 전체 추천 세션 로그 | user_id, location, goal, decibel, recommendation_reason, latency_ms, created_at |
| `spotify_link_click.xlsx` | 딥링크 클릭 로그 | playlist_id(FK), minutes_from_creation, clicked_at |
| `reviews.xlsx` | 사용자 피드백 | rating(0~4), will_reuse, dislike_reason, preferred_mood, feedback |

**사전배포 규모**: 18명, 약 300건 (2026-01-01 ~ 01-17)

### 왜 이 데이터가 문제 해결에 적합했는가

세 외부 데이터셋은 각각 독립적으로는 부분적인 인사이트만 줍니다. 그런데 **연결하면 추천 로직의 임계값**이 나옵니다.

```
환경공단 → "카페의 평균 소음은 59.5dB이고 변동성은 중간이다"
          ↓
RAED    → "같은 카페에서 공부할 때(44.8dB)와 식사할 때(67.6dB)는 23dB 차이다"
          ↓
Spotify → "44dB대 집중 상황에는 instrumentalness 0.83의 lofi가, 67dB대엔 energy 0.64+ pop이 적합하다"
```

이 연결 구조가 없으면 "집중할 땐 lofi가 좋다"는 감에 머뭅니다. 연결이 있으면 "카페에서 집중할 때라도 소음이 40dB대면 lofi, 60dB대면 팝"이라는 맥락 기반 로직이 됩니다.

## 5. 분석 흐름

### 단계별 과정 — 무엇을 / 왜 / 어떤 의사결정을

**Step 1. 문제 재정의 — "정확함"이란 무엇인가**

추천 시스템의 표준 평가 지표인 Precision, Recall, NDCG는 모두 정답 레이블을 전제합니다. "사용자가 이 상황에서 실제로 들을 법한 음악"이라는 정답 데이터가 없는 LLM 추천에서는 평가 자체가 문제였습니다.

**의사결정**: 표준 지표를 포기하고, 서비스 맥락에서 "잘 됐다"는 신호를 찾는 방향으로 전환. → 행동 기반 지표(DLC)와 텍스트 기반 정확도(Context Accuracy)를 자체 설계.

---

**Step 2. 추천 로직 근거 수치화 (외부 데이터 3종 분석)**

*환경공단 데이터*: 14종 측정 환경을 서비스 7개 장소로 매핑하고 소음 5구간을 정의했습니다. 단순 평균만 쓰지 않고 표준편차(변동성)까지 분석한 이유는, 같은 평균 소음이라도 이동 중(안정적 고소음)과 집(이벤트성 고소음)은 추천 전략이 다르기 때문입니다.

주요 결과: home(53.4dB, 변동 큼) < library(57.4dB) ≈ co-working(57.5dB) < cafe(59.5dB) < moving(67.0dB, 변동 작음)

*RAED 데이터*: 행동별 실제 소음·활동량을 수치화했습니다. 핵심 발견은 "장소보다 행동이 소음을 더 강하게 결정"한다는 점이었습니다. 침실에서 스트레스받은 상태(86dB)가 도서관에서 공부하는 것(44dB)보다 시끄러웠습니다. 이것이 장소 정보만이 아닌 실시간 소음 측정이 필수라는 설계 근거가 됐습니다.

*Spotify 데이터*: 장르별 오디오 특성(energy, instrumentalness, valence, tempo 등) 평균 프로파일을 만들어, 각 소음·목표 조합에 수치 기준을 대응시켰습니다.

---

**Step 3. 추천 우선순위 설계**

세 데이터셋을 연결한 결과, 추천 변수의 우선순위를 명확히 정의할 수 있었습니다.

| 우선순위 | 변수 | 역할 |
|---|---|---|
| 1 | **소음 수준** | 음악의 가청성과 직결. 80dB 초과 시 목표에 무관하게 소음 마스킹 최우선 |
| 2 | **사용자 목표** | 음악 분위기·장르 결정 |
| 3 | **위치** | 보조적 분위기 보정 |

**의사결정 포인트**: 이 우선순위를 초기에 명확히 정의해 두었기 때문에, 이후 LangGraph 추천 엔진의 모든 노드가 일관된 방향성을 가질 수 있었습니다.

---

**Step 4. 추천 엔진 설계 — 3번의 방향 전환**

| 버전 | 방식 | 문제 | 결정 |
|---|---|---|---|
| v1.0 | Rule-based | 168개 조합 룰의 복잡성, 다양성 부족 | 폐기 |
| v1.5 | 단순 GPT 호출 | 할루시네이션 (존재하지 않는 곡·아티스트 생성) | 폐기 |
| v2.0 | **LangGraph + Spotify API** | — | 채택 |

v2.0의 핵심 설계 원칙은 역할 분리입니다. LLM은 상황 해석과 장르 판단만 하고, 실제 곡 검색은 Spotify API가 담당합니다. 할루시네이션을 구조적으로 차단하는 방식입니다.

---

**Step 5. KPI 설계 — 8개 후보에서 5개로 압축**

8개 후보 KPI를 검토한 결과 3개가 탈락했습니다.

- **엔진 구조로 이미 해결된 것** (Search Hit Rate, Personalization Precision, Diversity): 추천 엔진 설계 자체에 내재화되어 별도 측정이 불필요.
- **API 제약으로 불가능한 것**: Spotify Audio Features/Recommendations API가 신규 앱에 403 차단(2024-11-26). 오디오 특성 기반 정밀 필터링 포기 → 키워드 매칭 기반으로 타협.
- **DB 설계 이슈로 불가능한 것** (Re-roll Rate): retry 세션이 신규 세션과 동일 형태로 기록되어 구분 불가.

**의사결정 포인트**: 측정 불가능한 것을 포기하고, 측정 가능한 지표로 범위를 재조정. 단, 각 지표의 한계를 함께 명시해 수치를 곧이곧대로 받지 않는 태도를 견지.

---

**Step 6. 사전배포 제안 및 로그 스키마 설계** ← 팀 원안에 없던 단계

팀 일정에는 사전배포가 포함되어 있지 않았습니다. 그러나 실사용자 로그 없이는 설계한 KPI 중 어느 것도 실측이 불가능했습니다. "로그 없이는 KPI 측정 불가"라는 논리로 팀을 설득했고, 수집할 로그 스키마(어떤 데이터를 어떤 형태로 저장할지)를 DA가 직접 정의해 개발팀에 전달했습니다.

---

**Step 7. 사용자 로그 분석 — 6가지 분석 수행**

경향성 분석 → 만족도 분석 → 세그먼트 분석 → 빈도 분석 → 시계열 분석 → 최신성 분석 순으로 진행했습니다. 단순 현황 파악에 그치지 않고, 각 분석이 개선 방향을 향하도록 설계했습니다.

---

**Step 8. 분석 결과 → 팀 의사결정 반영**

이탈 원인 분석이 완료된 후, 분석 결과를 팀에 공유했습니다. 이 결과는 "개인화 기능 도입 시 응답 속도 모니터링을 강화"하는 방향으로 개발 우선순위 변경으로 이어졌습니다.

---

## 6. 주요 분석 결과

### ① Deep Link Conversion (DLC) 85.15% — 가장 신뢰도 높은 지표

추천 결과를 본 사용자 중 85.15%가 Spotify에서 실제로 재생을 시도했습니다. 설문 응답이나 텍스트 분석과 달리, 클릭이라는 행동으로 측정한 수치이기 때문에 추천 수용도의 가장 솔직한 신호입니다.

그러나 상황별로 보면 뚜렷한 약점이 드러납니다.

| 상황 조합 | DLC |
|---|---|
| 카페 × 분노 | **0%** |
| 도서관 × 위로 | 25% |
| 코워킹 × 미설정 | 40% |
| 도서관 × 휴식 | 50% |
| 카페 × 위로 | 50% |

공공 공간(카페, 도서관)에서 개인적인 감정 케어(분노, 위로)를 요청하는 조합에서 전환율이 급락합니다. 장소의 공적 성격과 사용자의 감정 상태가 상충할 때 추천 로직이 약해진다는 근거입니다.

**추가 발견**: DLC와 지연 시간 사이에 뚜렷한 상관관계가 없었습니다. 사용자는 응답 속도보다 추천의 적절성을 더 중시한다는 의미입니다.

---

### ② 맥락 기반 일관 사용 패턴

사용자들은 무작위로 서비스를 사용하지 않았습니다. 히트맵 분석 결과 카페×집중·활력, 집/실내×휴식·수면, 코워킹×집중·활력, 헬스장×활력이라는 일관된 조합이 나타났습니다.

이것은 단순한 사용 현황 이상의 의미를 가집니다. RAED 데이터를 바탕으로 설계한 추천 로직이 실제 사용 맥락과 정합한다는 간접 검증이기도 합니다.

---

### ③ 만족도 3.27/4.0, 재사용 의사 93.3%

단, 18명이라는 표본 특성상 1~2명의 응답이 전체 수치에 크게 영향을 미칩니다. 절대 수치보다는 방향성 지표로 해석합니다.

주목할 점은 세그먼트 간 사용 빈도 차이입니다.

| 그룹 | 평균 사용 횟수 |
|---|---|
| 충성파 (평점 ≥3.0 & 재사용 Yes, 15명) | **23.3회** |
| 이탈 위험파 (평점 ≤2.0 & 재사용 No, 2명) | **6회** |
| 기타 | 16회 |

만족이 사용 빈도와 직결되는 선순환 구조가 확인됩니다. 초기 몇 회의 추천 경험이 장기 사용 여부를 결정하는 분기점이 된다는 의미입니다.

---

### ④ 이탈 원인 — 단일 원인이 아니다

이탈 위험파 2명의 피드백을 개별 분석한 결과, 이탈 원인이 서로 다른 방향이었습니다.

- **user 14** (1월 6일 이탈): "좋아하는 장르가 아니에요. J팝 가수 두 명과 인디 가수 한 명을 선호 가수로 선택했는데..." → **추천 품질** 문제
- **user 11** (1월 12일 이후 이탈): "플레이리스트가 나오는 데 너무 오래 걸려요" → **시스템 성능(응답 속도)** 문제

시계열 분석으로 이탈 시점과 시스템 이벤트를 연결한 결과, 1월 6일 개인화 기능 도입 이후 1월 12일까지 응답 시간이 일시적으로 상승했고, 이것이 user 11의 이탈로 이어졌습니다. 신기능 도입 직후 성능 모니터링이 중요하다는 구체적인 근거가 됩니다.

---

### ⑤ Agent Latency 시계열 — 단순 우하향이 아니다

상관계수 -0.2231만 보면 "시간이 지날수록 응답이 빨라졌다"로 읽힐 수 있습니다. 그러나 실제 시계열은 **안정(7초대) → 급등(개인화 도입 후 14초대) → 급락(최적화 후 3초대)** 구조입니다.

이 패턴이 중요한 이유: 단선적 개선이 아니라 기능 도입이 성능에 미치는 영향을 시각화했기 때문입니다. 수치 하나보다 패턴이 더 많은 것을 말해줍니다.

---

### ⑥ Satisfaction RMSE 1.1353 — "틀린 모델"의 가치

지연 시간만으로 만족도를 예측하는 단순 모델(`Predicted = 4.0 − 0.15 × latency_sec`)의 RMSE가 1.14입니다. 즉, 이 모델은 평균 1점 이상 틀립니다.

이 결과의 진짜 가치는 틀렸다는 사실 자체에 있습니다. "응답 속도가 빠르면 만족도가 높다"는 직관을 수치로 반박했고, 콘텐츠 품질 지표(Context Accuracy, 장르 일치도)를 모델에 추가해야 한다는 다음 방향을 도출했습니다.

## 7. 핵심 인사이트

### 인사이트 1. "카페 = 집중 음악"은 틀린 공식이다

장소만 보면 카페는 집중 음악의 대표 공간처럼 보입니다. 그러나 데이터는 다른 이야기를 합니다. RAED 기준으로 카페에서 공부할 때는 44.8dB, 식사할 때는 67.6dB로 약 23dB 차이가 납니다.

비즈니스적 의미: 추천 로직에서 장소를 단독 기준으로 쓰는 것은 틀립니다. 같은 카페라도 소음 수준에 따라 lofi(저소음+집중)와 팝(고소음+집중)으로 분기해야 합니다. 이것이 앱이 사용자 휴대폰의 소음 센서를 실시간으로 측정하는 설계 근거이기도 합니다.

---

### 인사이트 2. 공공 공간에서 개인 감정 케어는 추천 시스템의 사각지대다

카페-분노(DLC 0%), 도서관-위로(25%) 데이터가 말하는 것은 단순한 성능 문제가 아닙니다. 카페나 도서관 같은 공공 공간에서 "분노 해소" 또는 "위로"를 요청하면, 추천된 음악이 공간의 사회적 맥락과 충돌합니다. 헤드폰이 전제된 상황에서도 분위기가 맞지 않는 곡은 클릭으로 이어지지 않습니다.

비즈니스적 의미: 음악 추천이 음악 특성 이외에 공간의 사회적 성격까지 고려해야 한다는 것. 이 조합에 대한 추천 로직을 별도로 설계하거나, 사용자에게 "이 상황에서는 헤드폰 착용을 권장"하는 맥락적 안내를 추가하는 방향이 가능합니다.

---

### 인사이트 3. 초기 몇 회가 장기 사용 여부를 결정한다

충성파(23.3회 사용)와 이탈 위험파(6회 사용)의 차이는 누적됩니다. 그런데 시계열을 보면 이탈 위험파의 이탈은 초반에 집중됩니다. 초기 경험이 기대를 충족하지 못하면 회복이 어렵습니다.

비즈니스적 의미: 신규 사용자의 초기 3~5회 추천 품질을 최우선으로 관리해야 합니다. 특히 기능 업데이트나 시스템 변경 시 일시적 성능 저하가 신규 이탈로 직결될 수 있으므로, 변경 직후 일주일간 집중 모니터링 체계가 필요합니다.

---

### 인사이트 4. 지연 시간이 아닌 적합성이 만족도를 결정한다

RMSE 1.14와 DLC-Latency 상관관계 부재가 동일한 결론을 향합니다. 사용자는 7초 기다리더라도 상황에 맞는 음악을 받으면 실제로 듣습니다. 반대로 1초 만에 나온 추천이라도 내 상황과 맞지 않으면 클릭하지 않습니다.

비즈니스적 의미: 성능 최적화(속도 개선)보다 맥락 정확도 개선(더 잘 맞는 추천)이 만족도와 직결됩니다. 개발 리소스 배분에서 속도보다 품질 개선을 우선해야 한다는 데이터 기반 근거입니다.

### 음악 스트리밍 서비스 관점

**추천 품질 고도화**: DLC 기반 상황별 약점 지도(카페-분노 0%, 도서관-위로 25%)는 추천 로직 개선의 우선순위 지도로 바로 활용 가능합니다. 전환율이 낮은 상황 조합부터 집중 개선함으로써 전체 전환율을 높이는 것이 효율적입니다.

**개인화 기능 도입 전략**: 개인화 도입 후 응답 시간 급등 → 이탈 발생 패턴은, 신기능 출시 시 A/B 테스트와 성능 모니터링을 선행해야 한다는 실증적 근거입니다. 전체 롤아웃 전 소규모 코호트 테스트 단계 추가를 정당화할 수 있습니다.

**신규 사용자 온보딩 전략**: 초기 경험이 장기 충성도를 결정한다는 데이터를 바탕으로, 첫 3회 추천에 더 높은 품질 기준을 적용하거나 초기 사용자에게 추가 입력(취향 수집)을 유도하는 플로우를 설계할 수 있습니다.

### LLM 서비스 전반으로의 확장

이 프로젝트에서 사용한 "행동 기반 전환율로 추천 품질을 간접 측정"하는 방식은, 정답 레이블이 없는 모든 LLM 생성 콘텐츠 서비스(뉴스 요약, AI 글쓰기 보조, 챗봇)에 적용 가능한 프레임워크입니다.

### 운영 효율화

Context-Sentiment Accuracy 19% 미달 분의 주요 원인이 키워드 대신 유의어 사용임을 확인했습니다. 이는 Semantic Similarity 기반 평가 도입으로 해결 가능한 구체적인 방향을 제시합니다. 개발 리소스를 어디에 투입할지 우선순위 결정에 데이터 기반 근거를 제공합니다.

## 11. 포트폴리오에서 강조해야 할 차별점

### 차별점 1. "분석할 환경"을 직접 만들었다

대부분의 포트폴리오 프로젝트는 이미 존재하는 데이터를 분석합니다. 이 프로젝트에서는 분석에 필요한 데이터가 존재하지 않는 상황에서, 사전배포를 제안하고 로그 스키마를 직접 설계해 데이터를 만들었습니다.

"측정할 수 없으면 개선할 수 없다. 그렇다면 측정 가능한 상태부터 만들어야 한다"는 논리로 팀을 설득한 경험은, 데이터 분석가의 역할을 "분석하는 사람"이 아니라 "분석 가능한 상태를 설계하는 사람"으로 확장합니다.

왜 경쟁력 있는가: 실무에서는 분석에 필요한 로그가 항상 존재하지 않습니다. 어떤 로그를 어떤 형태로 수집해야 하는지를 설계할 수 있는 분석가는 수동적 수용자가 아니라 시스템의 공동 설계자입니다.

---

### 차별점 2. 없던 기준을 직접 만들었다 (KPI Zero-Design)

Precision, Recall, NDCG처럼 계산만 하면 되는 지표가 아니라, "이 서비스에서 좋은 추천이란 무엇인가"라는 질문 자체를 데이터·서비스 맥락에서 정의했습니다.

8개 후보 KPI 중 3개가 탈락한 사유를 기록한 것도 차별점입니다. 수치를 제시할 때 그 수치의 한계(측정 기준의 관대함, 표본 크기 등)를 함께 서술하는 태도는, 데이터를 맹신하지 않는 분석 역량을 보여줍니다.

---

### 차별점 3. 분석이 실제 결정으로 이어졌다

이탈 원인 분석 → 팀 공유 → 개발 우선순위 변경. 보고서가 서랍 속에 들어가지 않고 실제 팀의 행동을 바꾼 경험은, 분석가의 가장 중요한 역할인 "분석 결과를 조직 결정으로 연결"을 입증합니다.

---

### 차별점 4. 이종 데이터 연결로 새로운 임계값을 도출했다

환경공단(장소별 소음) + RAED(행동별 실제 소음) + Spotify(음악 특성)를 연결해 "카페+40dB=lofi, 카페+60dB=팝"이라는 상황별 추천 기준을 수치로 만든 것은, 단일 데이터셋 분석으로는 나올 수 없는 결론입니다. 데이터 결합 설계 자체가 분석 역량의 증거입니다.

---

## 12. 채용 담당자 관점에서 가장 경쟁력 있는 경험 TOP 3

### 경험 1. 사전배포 제안 — 분석 환경을 직접 설계한 경험

**경험**: 팀 원안에 없던 사전배포를 논리로 설득해 실행시키고, 수집할 로그 스키마를 DA가 직접 정의해 18명·약 300건의 실사용자 데이터를 확보했습니다.

**왜 중요한가**: 실무에서 분석가는 항상 "있는 데이터"만 받지 않습니다. 어떤 데이터를 어떻게 쌓아야 하는지를 판단하고 관계자를 설득하는 역량이 필요합니다. 이 경험은 그 역량을 직접 증명합니다.

**보여주는 역량**

- **문제 정의**: "로그 없이는 KPI 측정 불가"라는 핵심 제약을 먼저 발견
- **비즈니스 이해**: 단순히 분석을 요청하는 것이 아니라, 어떤 로그가 어떤 분석에 필요한지를 역산해 스키마 설계
- **실행력**: 팀 설득부터 스키마 전달, 데이터 수집까지 end-to-end 실행
- **협업**: 앱 종료 로그·저장 로그 등 구현 난이도가 높은 항목은 개발팀과 협의해 제외하는 현실적 조율

---

### 경험 2. 이탈 원인 분석 → 개발 우선순위 변경

**경험**: 이탈 위험파 2명을 개별 심층 분석해 이탈 원인이 추천 품질(user 14)과 응답 속도(user 11) 두 가지로 나뉜다는 것을 발견하고, 시계열로 개인화 도입 시점과 연결해 팀에 공유했습니다. 이 결과가 "개인화 도입 시 응답 속도 모니터링 강화"로 개발 우선순위를 실제로 바꿨습니다.

**왜 중요한가**: 분석가의 가치는 수치를 계산하는 것이 아니라 그 수치가 조직 결정에 영향을 미칠 때 실현됩니다. "분석 → 의사결정"의 완결된 사이클을 보여주는 가장 강력한 경험입니다.

**보여주는 역량**

- **데이터 분석**: 소규모(2건) 이탈 데이터를 피상적으로 처리하지 않고, 피드백·시계열·시스템 이벤트를 교차 분석해 원인을 구분
- **비즈니스 이해**: "이탈은 단일 원인이 아니다"는 인사이트를 실무 적용 가능한 대응 방향으로 연결
- **스토리텔링**: 분석 결과를 비데이터 직군이 이해하고 행동으로 옮길 수 있게 전달
- **협업**: 분석이 개발팀의 우선순위 결정에 실제로 반영되는 협업 구조 형성

---

### 경험 3. KPI를 0에서 직접 설계하고 측정 한계를 명시한 경험

**경험**: 정답 레이블도 표준 지표도 없는 LLM 추천 환경에서 8개 후보 KPI를 설계하고, 각 탈락 사유(API 제약, DB 설계 이슈, 측정 불가)를 명시한 뒤 최종 5개를 실측했습니다. Persona-Genre Accuracy 100%가 "완벽한 반영"이 아니라 "관대한 키워드 포함 기준"임을 함께 서술했습니다.

**왜 중요한가**: 수치를 만드는 것보다 그 수치를 얼마나 신뢰할 수 있는지를 아는 것이 더 어렵습니다. 지표의 한계를 함께 제시하는 태도는, 잘못된 수치로 잘못된 결정을 내리지 않는 분석 역량의 핵심입니다.

**보여주는 역량**

- **문제 정의**: "무엇을 측정해야 하는가"를 서비스 맥락에서 처음부터 정의
- **데이터 분석**: API 제약, DB 설계 이슈, 표본 크기 한계를 인식하고 현실적으로 대응
- **비즈니스 이해**: 각 KPI가 비즈니스 맥락에서 무엇을 의미하는지 해석
- **스토리텔링**: "100%"라는 수치를 맹신하지 않고 측정 기준의 한계를 투명하게 서술

## 13. 포트폴리오 구성 제안 (웹 포트폴리오 기준)

채용 담당자가 3분 안에 프로젝트를 이해할 수 있도록 구성합니다.

---

### 섹션 1. 헤드라인 카드 (15초)

**제목 제안**: "LLM이 음악을 추천하면, 잘 됐다는 걸 어떻게 알 수 있나요?"

**핵심 메시지**: 정답 없는 AI 추천을 평가하는 기준을 직접 설계한 프로젝트

**강조 수치 (4개 숫자로 요약)**:
- DLC 85.15%
- Context Accuracy 81.17%
- 18명 실사용자 로그 수집
- 분석 결과가 팀 개발 우선순위를 변경

**추천 시각화**: 프로젝트 전체 흐름도 (데이터 수집 → 로직 설계 → KPI 설계 → 사전배포 → 분석 → 의사결정)

---

### 섹션 2. 문제 정의 (30초)

**제목 제안**: "LLM 추천에는 정답이 없다 — 그래서 기준을 만들었다"

**핵심 메시지**: 측정할 기준이 없으면 개선도 없다. 기준 설계 자체가 분석의 시작이었다.

**추천 시각화**: KPI 8개 → 5개 탈락 사유 정리표 (왜 각 지표를 채택·폐기했는지)

---

### 섹션 3. 데이터 연결 — 핵심 차별점 (45초)

**제목 제안**: "3개 데이터셋을 연결해 '카페+40dB = lofi'를 수치로 만들었다"

**핵심 메시지**: 이종 데이터 연결이 감이 아닌 근거를 만든다

**추천 시각화**: 
- 3개 데이터셋 연결 다이어그램 (환경공단 → RAED → Spotify → 추천 로직)
- 행동별 소음 수치 비교 차트 (sleeping 27.7dB ~ stressed 87.5dB)
- 상황별 추천 매트릭스 테이블

---

### 섹션 4. 핵심 분석 결과 — 숫자로 말하기 (60초)

**제목 제안**: "85%가 실제로 들으러 갔다 — 하지만 전부가 아니다"

**핵심 메시지**: 전체 DLC 85.15%는 강점, 카페-분노 0%는 약점. 데이터는 강점만큼 약점도 정직하게 보여준다.

**추천 시각화**:
- Location × Goal DLC 히트맵 (색상 강도로 전환율 표시 — 약점 조합 한눈에 확인)
- Agent Latency 시계열 (안정→급등→급락 스토리)
- 충성파 vs 이탈위험파 사용 빈도 비교 차트

**강조해야 할 성과**: 카페-분노 0%, 도서관-위로 25% — "어디가 문제인지" 특정했다는 것 자체가 성과

---

### 섹션 5. 분석이 결정을 바꾼 순간 (30초)

**제목 제안**: "이탈 분석이 개발 우선순위를 바꿨다"

**핵심 메시지**: 분석은 보고서가 아니라 결정으로 완성된다

**추천 시각화**: 이탈 원인 두 갈래 다이어그램 + 시계열(이탈 시점 & 시스템 이벤트 연결)

---

### 섹션 6. 배운 것과 한계 (15초)

**제목 제안**: "잘 됐던 것과 아쉬운 것을 모두 기록했다"

**핵심 메시지**: 한계를 솔직히 서술하는 분석가가 수치를 맹신하지 않는다

**강조해야 할 성과**: Persona-Genre Accuracy 100%의 측정 한계 명시, 표본 18명의 해석 주의, DB 설계 단계에서 분석 관점을 미리 반영해야 한다는 교훈

### 현직 데이터 분석가 관점에서 보완하면 좋을 점

**보완점 1. A/B 테스트 또는 인과 추론 근거 보강**

현재 분석은 관찰 데이터 기반입니다. "개인화 도입 → 응답 시간 증가 → 이탈"이라는 흐름은 설득력이 있지만, 인과 관계를 엄밀하게 증명하지는 않습니다. `[확인 필요]`로 표시된 A/B 테스트 수행 여부를 확인하고, 있다면 반드시 포함하세요. 없다면 "표본 18명으로 인과 관계를 증명하기엔 한계가 있다"는 명시가 오히려 신뢰성을 높입니다.

**보완점 2. Context Accuracy의 Semantic Similarity 보강**

현재 Context-Sentiment Accuracy(81.17%)는 키워드 매칭 기반입니다. "집중"이라는 단어 대신 "편안한"을 사용한 경우를 미달로 처리한 방식의 한계를 인지하고 있다면, 간단한 word embedding 유사도(cosine similarity)나 sentence-BERT 기반 시뮬레이션 예시를 추가하면 "다음 버전에서 이렇게 개선할 것"이라는 방향을 보여줄 수 있습니다.

**보완점 3. 더 많은 수치를 히트맵으로 시각화**

Location×Goal DLC 히트맵은 강력한 시각화입니다. 여기에 두 번째 레이어로 "세션 수"(데이터 신뢰도)를 함께 표시하면 — 예를 들어, 카페-분노가 0%인데 세션 수가 3건이라면 신뢰도가 낮다는 것을 함께 보여줄 수 있습니다. 수치의 해석에 맥락을 더하는 방법입니다.

**보완점 4. "다음에는 이렇게 한다"를 더 구체적으로**

회고에서 "다시 한다면" 항목이 있습니다. 이를 포트폴리오 마지막 섹션에 포함하면 성장 가능성을 보여주는 강력한 마무리가 됩니다. 특히 "EDA 결과가 이미 ground truth였다는 회고" — Audio Features API 없이도 직접 구현할 수 있었다는 발견 — 은 문제를 해결하면서 얻은 진짜 인사이트입니다.

**보완점 5. 충성파 선호도 데이터 활용**

충성파(15명)의 선호 패턴 — energetic 70.4%, lyrics_on 88.9% — 은 단순 현황 이상입니다. 이것이 "충성파를 더 만들기 위해 초기 추천에서 energetic + lyrics_on 조합을 강화해야 한다"는 비즈니스 제안으로 이어지면 분석 → 액션 연결의 또 다른 사례가 됩니다.
